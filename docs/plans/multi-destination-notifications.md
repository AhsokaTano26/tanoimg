# 多目标通知实施方案

## 目标

一条登录、上传或审核事件可同时送达多个邮件、通用 Webhook、Telegram 与 Server酱目标，同一类型允许多个实例。新增 Webhook 使用用户提供的 `/webhook/general` JSON 协议，URL 由管理员填写。旧单渠道配置升级后仍能正常发送。

## 配置与兼容

- 在原全局开关和事件类型开关下，新增 `channels` 列表。每项有稳定 ID、启用状态、显示名称、渠道类型和对应配置。
- 老配置没有 `channels` 时，将现有 `method` 与配置视为一个 `legacy` 目标；读取接口返回可编辑的目标列表。新保存采用列表格式。旧自定义 Webhook 模板继续用兼容模式发送，新建 Webhook 默认采用通用 JSON 协议。
- 后台页面允许增删、启停与单独测试目标，所有表单继续使用封装控件。

## 投递与失败处理

- 入队时为每个启用目标插入独立的队列记录，记录目标 ID。同一目标失败只重试自身，不重发已成功目标。目标被删除或停用后，其待发记录跳过。
- 旧队列记录没有目标 ID，投递给迁移后的 `legacy` 目标，沿用原模板；该目标删除或停用后跳过。每个目标独立保留现有三次重试与任务中心错误状态。
- 通用 Webhook 使用 POST、`Content-Type: application/json`，只发送协议允许的字段：`message`、`title`、`source`、`level`、`timestamp`、`fields`、`url`。级别按事件映射；可用的绝对图片链接放入 `url`，其余标量数据放入 `fields`。排版后超过 1900 字符则报错，不截断内容。

## 验收

测试覆盖旧配置迁移、同类与异类目标并存、协议字段和长度、单目标失败不会使其他目标重复投递、目标停用与测试发送。前端测试、Go 测试、`make build` 通过，并按阶段提交。
