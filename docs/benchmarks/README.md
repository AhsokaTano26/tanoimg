# 2026-09-25 本机性能测量

共完成 60 组有效测试（不含两组早期中断探测），其中普通上传阶梯 36 组、万张上传 6 组、转换 6 组、图库读取 9 组、原图热读 3 组。本目录保留原始 JSONL、硬件/二进制信息及汇总 CSV；根目录 [PERFORMANCE.md](../../PERFORMANCE.md) 提供结论、图表和完整分析。复现命令与指标定义见 [压测工具](../../tools/loadtest/README.md)。

## 范围与口径

- 生产服务二进制使用 `292fd2b` 的业务代码；后续提交仅增加压测工具和文档。客户端、服务端分进程运行。
- 原生环境：Apple M4 Pro，14 核，24 GiB，macOS/APFS。容器环境：Docker Desktop Linux arm64，匿名持久卷，2 vCPU，分别设置 `--memory=1g/2g --memory-swap=1g/2g`。没有使用 macOS 绑定目录承载容器数据库。
- PNG 内容来自密码学随机 RGBA 像素，基本不可压缩，256×256 约 256 KiB，724×724 约 2 MiB。每轮使用同一张图片多次上传，服务端每次生成独立文件和记录，不做去重。
- 普通上传使用默认配置，关闭压缩/格式转换；API Key 认证，HTTP/1.1，完整消费响应体，无自动重试。
- 这里的并发是同时在途的请求数，不等于在线用户数。
- 每个阶梯发送 8 秒，等待已发请求结束；记录实际完成耗时。并发为闭环客户端数，每个客户端收到响应后再发下一个。测试范围 1–128 个上传客户端。
- 峰值是所测条件下的观测值，不代表所有图片格式、尺寸、网络、磁盘、共享 CPU 或持续运行条件下的绝对极限。
- 所有请求来自同一台机器。未测长期混合读写、所有格式/尺寸组合、TLS、CDN、真实公网、Zeabur 节点、跨机网络、匿名自动封禁、审核/通知外部服务，也没有把被拒绝请求算成成功吞吐。

## 计算

```text
成功吞吐 = 完整确认的 HTTP 200 数 / 实际耗时
错误率 = (总请求数 - 成功数) / 总请求数
成功上传 MiB/s = 成功数 × 单图字节数 / 实际耗时 / 2^20
万张估算耗时 = 10000 / 成功吞吐
10 分钟万张最低吞吐 = 10000 / 600 = 16.67 张/秒
```

实际固定数量测试直接使用实测耗时，不能将短测折算值称为万张实测。

## 过载与测试边界

初次测试脚本在两组过载场景的核对断言处停止：一组为客户端完整确认数与落库数不一致，另一组为停服时文件数与记录数不一致。前者改为保留差异指标；后者在脚本停服前增加 2 秒排空等待，然后重测对应并发。早期未完成的两组不作为有效性能结论。原始 JSONL 中前期记录没有 `drain_seconds`，后续记录明确为 2。

macOS 过载场景出现传输错误、429，以及“已落库但客户端未完整确认”的差异。这意味着超时/连接错误后的盲目重传可能产生重复图片，不能把这些场景表述为零错误或无损。没有在本次压测任务中修改生产上传行为。

内存必须区分：进程 RSS、Go 堆、容器 cgroup 总占用。容器 cgroup 包括文件页缓存和内核内存；接近内存限额并不等于进程把同等内存全部分配到堆。`memory.events.max` 可能记录缓存回收压力；判断 OOM 要看 `oom` / `oom_kill` 和容器退出状态。内存峰值包含服务启动，读取测试还包含准备图库阶段。内核允许某些情况下短暂超过 `memory.max`，因此原始峰值略大于 1024 MiB 不代表未设置限制；参见 [Linux cgroup v2 官方定义](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory-interface-files)。

1 GiB/2 GiB 是应用容器限额；不能等同于整台 1 GB/2 GB 云服务器的可用应用内存，后者还要承担内核、运行时、代理等。增加内存不会改变代码中的 4 个上传处理槽、32 个等待槽、单 SQLite 连接以及单图片转换槽；不能通过“总内存 ÷ 本次 RSS”推导安全并发。
